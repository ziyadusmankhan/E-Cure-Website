# Content and staff workflows

Phase 8 adds a private management boundary under `/api/admin/`, separate from public submission endpoints. Every page and API verifies the opaque server session and required MFA. Transactions then recheck active staff membership, role, issuer, expiry and the deployment profile. Shared provisioning locks prevent an operator changing staff membership during a management transaction. Runtime retains read-only access to administrative identity mappings.

Owners manage all requests and content. Receptionists see and update only assigned appointments/inquiries, and customer details reached through their assigned appointments. Assignment and CSV export require Owner permission. Request updates use row locks and optimistic versions; conflicting edits return 409. Status, assignment and bounded administrative notes append to immutable workflow history in the same transaction. General audit records contain structural identifiers only. Customer records contain contact and appointment information, not medical records. Exports contain up to 1,000 filtered appointment results with quoted, formula-escaped cells.

The singleton `cms_state` holds complete public-only draft and published documents. Each draft save requires the current revision. Publication validates content, resolves image references and updates the published snapshot, live service eligibility, business settings and page rows in one transaction. Removed services are disabled in the live catalog; historical appointments retain their service foreign keys. Discard restores the live document while advancing the revision. Public renderers read only the published snapshot. Root rendering is dynamic, with a request-scoped React cache, so content cannot remain frozen in build-time pages. Server page snapshots also refresh the persistent client header/footer on navigation.

Content fields are allowlisted and rendered as plain text. Consent, submission receipts and security notices cannot be rewritten through the editor. The existing theme presets remain available; custom text colors must meet the configured 4.5:1 contrast threshold. Public URL/deployment identity and advanced SEO remain outside this phase. A ten-minute HttpOnly preview preference can expose a draft only after fresh Owner authorization; anonymous or expired sessions see published content. Preview image requests also require Owner authorization.

Uploads accept JPEG, PNG and WebP input up to 2 MB, 4,096 pixels per dimension and 16 million pixels. Sharp decodes and reencodes a single-frame image to bounded WebP, stripping metadata. Logos resize inside 512 pixels; other images inside 1,600 pixels. SVG, animation, malformed input and oversized images are rejected. Private database media is public only after a publication references it. Published media identifiers are immutable; replacing an image creates a new identifier. This is a bounded foundation for website assets, not a patient-document store. An unused-upload retention policy and deployment-specific object storage remain operational follow-up work. Processing follows Sharp's [input limits](https://sharp.pixelplumbing.com/api-constructor/) and [resize behavior](https://sharp.pixelplumbing.com/api-resize/).

## Local setup and use

1. Run `npm.cmd run db:local:start` and `npm.cmd run db:local:migrate`.
2. Run `npm.cmd run cms:local:initialize`. It is insert-only and preserves an existing draft. The database must already contain this deployment's reviewed business/profile foundation.
3. Set `CMS_MODE=database` in ignored `.env.local`, then restart the app. Default `CMS_MODE=disabled` keeps credential-free public fixtures available.
4. Start local Supabase Auth, then sign in at `/admin/login` using the private Owner credentials and complete authenticator setup if prompted.
5. Open **Website editor**, save draft changes, preview, and explicitly publish. Unpublished service changes do not alter public booking eligibility.

`npm.cmd run test:db` uses five disposable databases and covers management transactions alongside foundation, submission and controlled Auth checks. `npm.cmd run test:management` creates a separate disposable database and real ephemeral Supabase Auth/MFA identities for browser workflows. Run all database harnesses sequentially. The actual Owner and persistent development requests are excluded from test fixtures. CI is prepared; only locally executed verification is claimed.

Admin section destinations share a strict browser/server allowlist. A narrowly matched Next proxy overwrites the internal path header from the actual request URL; the protected layout uses it only to choose a safe section-level login destination. Layout, page/DAL and API authorization remain separate checks. No client-supplied route or role header grants access. Service detail pages render dynamically so newly published or disabled slugs never depend on a build-time path list.

Public CMS projections omit disabled services and their related-service references. Newly uploaded images referenced only by disabled services remain private when other changes are published; enabling and publishing the service makes its image public. Previously published image identifiers remain immutable public assets.
